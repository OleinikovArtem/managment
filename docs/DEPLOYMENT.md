# Размещение приложения

## Целевая схема

Приложение предназначено для небольшого числа участников и разворачивается как
Next.js-приложение на Vercel с общей PostgreSQL-базой Neon. Код хранится в GitHub;
Vercel подключается к репозиторию и автоматически собирает production после
обновления основной ветки. Локальный Docker для этого пути не требуется.

Целевые сервисы:

- **Vercel Hobby** — Next.js App Router, серверные обработчики и интерфейс.
- **Neon Free** — общая PostgreSQL-база для пользователей, групп и их данных;
  Prisma подключается через `@prisma/adapter-pg` и пулерное соединение Neon.
- **Vercel Blob** пока не используется. Не хранить постоянные данные в файловой
  системе Vercel Functions; загрузки файлов требуют отдельной реализации внешнего
  хранилища.
- **GitHub** — исходный код и история изменений; GitHub Pages не размещает
  динамическое Next.js-приложение.

Этот вариант рассчитан на личное некоммерческое использование в пределах
актуальных лимитов бесплатных тарифов. У Vercel Hobby есть ограничение на
коммерческое использование. Vercel и Neon — разные сервисы: бесплатный тариф
Vercel не включает PostgreSQL. Перед публикацией нужно повторно проверить
условия, квоты, лимиты функций, хранения и трафика у провайдеров.

## Хранение и обработка данных

- Все рабочие записи партий и учетные записи пользователей хранятся в общей
  серверной PostgreSQL-базе. Разделение доступа обеспечивается серверной
  авторизацией по участию пользователя в партии; клиентские `partyId` не являются
  разрешением на доступ.
- Общий каталог предметов хранится отдельно от данных партий; партийные
  псевдонимы и отображаемые варианты названий имеют область действия партии.
- Секреты подключения, сессий и шифрования задаются в переменных окружения
  production-проекта. Секреты не коммитятся в Git и не отправляются клиенту.
- Vercel Functions не используются как постоянно работающий процесс. Для
  Telegram применяется webhook: Telegram отправляет обновления на защищенный
  Route Handler приложения. Обработчик проверяет секрет webhook, chat и sender,
  затем передает событие в существующий финансовый сервис с идемпотентностью.
- Доставка Telegram-событий должна быть устойчивой к повторной отправке и
  ошибкам запроса. Сетевой обработчик подтверждает событие только после его
  надежной фиксации; финансовая запись и идентификатор Telegram-события должны
  сохраняться атомарно.
- Секреты ботов каждой партии шифруются серверным ключом. Ключ хранится в
  deployment secrets отдельно от базы.

## Перенос с текущей локальной версии

Приложение и локальная разработка используют PostgreSQL. `compose.yaml` запускает
локальный экземпляр того же движка, а Prisma migrations находятся в
`prisma/migrations-postgresql/`. При Vercel production build выполняет `migrate
deploy` и применяет дополнительные ограничения из
`prisma/postgresql-constraints.sql` до сборки приложения.

Старая SQLite-база может содержать тестовые партии и финансовые записи; они в
новую PostgreSQL-базу не переносятся. Список предметов сохраняется отдельно:
`npm run db:catalog:import` открывает прежнюю `prisma/dev.db` read-only и переносит
только строки каталога в PostgreSQL. Не удалять старый SQLite-файл до успешного
импорта и проверки количества предметов. После импорта именно PostgreSQL содержит
актуальный общий каталог; новые и изменённые записи не синхронизируются обратно в
старую SQLite-базу.

Новый каталог `Item` общий для всех групп и имеет уникальность по
`normalizedName`. Очистка партии его не удаляет. Все записи предметов, рейдов,
участников и финансовых операций создаются заново в PostgreSQL после запуска.

Очистка группы использует PostgreSQL-транзакцию и локальную настройку
`app.party_reset`; провайдерские ограничения обходятся только в этой явной
операции. Локальные pg_dump выполняются через Docker Compose; production snapshots
и restore выполняются через Neon. SQLite backup/restore в приложении больше не
используется.

### Требования к миграции и выпуску

- Старую SQLite-базу не менять: каталог импортируется read-only скриптом, другие
  тестовые данные намеренно не переносятся.
- Проверить количество записей Item и совпадение ключевых полей каталога до
  первого добавления новых предметов в PostgreSQL.
- Не публиковать приложение без серверной авторизации и изоляции данных партии.
- Production env содержит `DATABASE_URL` (pooled Neon connection) и `DIRECT_URL`
  (direct Neon connection для Prisma migrations). Оба значения задаются в Vercel
  server-side environments и не коммитятся.
- До production необходимо перевести SQLite integration tests на отдельную
  disposable PostgreSQL database; текущие тесты не являются проверкой нового
  PostgreSQL runtime.
- Не хранить production-данные в SQLite-файле внутри репозитория или локального
  каталога Vercel.

## Эксплуатационные ограничения

- Neon Free — отдельный сервис и отдельная квота; возможны пауза/пробуждение
  compute и задержка первого запроса после простоя.
- Бесплатные квоты не являются обещанием бессрочной доступности. Настроить
  наблюдение за расходом квот и иметь экспорт/резервную копию, пригодную для
  восстановления.
- При переходе к коммерческому использованию, росте нагрузки или необходимости
  гарантированного SLA пересмотреть тарифы и хостинг.

## Статус

Инфраструктурная конфигурация проекта переведена на PostgreSQL: Docker Compose для
локальной базы и Neon как целевой production database. Vercel production build
настроен применять миграции. Сам аккаунт Neon/Vercel и deployment ещё не созданы;
публичный запуск отложен до реализации авторизации. Старый SQLite-файл остаётся
источником только для одноразового импорта каталога.
