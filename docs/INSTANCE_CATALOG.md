# Инстансы, стадии сервера и рекомендуемые предметы

## Области каталога

Существующие `Item` остаются глобальными с прежними ID. Nullable `partyId` у Item
и Instance означает общий каталог; пользователи, включая OWNER, видят его только
для чтения. Создание из интерфейса всегда создаёт собственную запись активной группы.
Собственные записи можно переименовать, архивировать и восстановить. Архив не
удаляет исторические поступления и связи; владелец записи не меняется.

Уникальность имени: partial unique index глобальных записей и `(partyId, normalizedName)`
для своих, включая архив. Собственный серверный вариант может иметь имя общего
предмета. Поиск и создание лута принимают только общие или свои записи. Прямые FK
не выражают global-or-own, поэтому SQL guards проверяют LootDrop, TelegramItemAlias,
quick items и custom presets. UI явно подписывает область каталога.

Bootstrap новых групп больше не изменяет общий каталог. Контролируемый импорт
каталога и metadata seed выполняются отдельно; повторный seed не создаёт групповые
копии. Все 19 instance codes определены в `prisma/seeds/instances.json`.
`npm run db:catalog:seed` добавляет отсутствующие базовые общие предметы и точные
названия из таблиц BOHPTS; существующие global/private строки не обновляются.
Инстанс Fortress отображается как `Fortress/Castle Dungeon`; «Подвал» остаётся
поисковым псевдонимом.
Неподтверждённые retail-варианты отмечены SERVER_VARIANT, источники — в
[GAME_DATA_SOURCES.md](./GAME_DATA_SOURCES.md).

## Три разных стадии

- Global Current: `ServerStageConfig('GLOBAL').explicitCurrentStageId`, если задан;
  иначе максимальная доступная опубликованная Stage по sequence.
- Party Default: `Party.selectedStageId`, если задан; иначе Global Current.
  OWNER/ADMIN меняют его только в Settings. Null означает автоматическое наследование.
- Raid Draft: конкретная стадия, скопированная из default при открытии формы.
  StageSwitcher формы меняет только этот черновик, без записи Party и влияния на
  другие открытые формы. Смена global/default не является конфликтом сохранения.

Доступная Stage имеет publishedAt и isSelectable=true. Draft-стадии не показываются.
Если выбранная стадия отключена или изменилась revision, создание возвращает
понятный конфликт без записи рейда. Пользователь обновляет рекомендации/выбирает
стадию и повторяет сохранение; весь черновик сохраняется. Если стадий ещё нет,
допустим рейд без Stage и без глобальных рекомендаций. Недоступную настройку пати
можно обойти локальным выбором доступной Stage, не меняя общий default.

Сохранённый Raid хранит stageId, code/name/revision snapshots. Обычный edit не
изменяет их даже при просмотре других рекомендаций. Старые null Stage остаются
«Стадия не указана»; массового backfill по текущей стадии нет.

## Предметы формы и сохранение

Компактная строка: инстанс, дата/время и Stage. Своё название необязательно;
если оно пустое, сохраняется подпись инстанса либо «Рейд». Составы, статусы и
Main/Subclass остаются отдельными полями. Рекомендации и выбранная добыча разделены:
смена инстанса/Stage не меняет предметы, количества, комментарии и участников.
Все предметы выбираются вручную. Нет преселекта, процентов или предположений о шансах.
sortOrder задаёт стабильный порядок отображения.

Глобальные рекомендации зависят от Instance и Stage. Пользователь не редактирует
их. На Stage 1 опубликованы таблицы пользователя для Lab 78 и Fortress/Castle
Dungeon. Их исходный порядок сохранён; количество и group chance хранятся только
как метаданные источника и не показываются как шанс или применяемое количество в
форме. Другие инстансы/стадии и быстрые наборы пати остаются пустыми. Собственный
инстанс имеет независимый от Stage набор; быстрый набор группы доступен для любого
инстанса и настраивается отдельно от истории.

Рейд, исходные участники и начальная добыча сохраняются атомарно. creationKey
уникален в группе: повтор идентичного успешного запроса возвращает тот же Raid;
другие данные с тем же использованным ключом — конфликт. Конфликт до записи не
расходует ключ. Исторические поступления одного Item остаются разными строками
со своими ID, комментариями и продажами; их нельзя объединить ради плиток.

## Административная публикация

Скрипты используют DIRECT_URL или DATABASE_URL из выбранной среды. Перед запуском
проверить целевую БД; приватные production env автоматически не подхватываются
Prisma CLI. Пользовательского endpoint для глобальных стадий/рекомендаций нет.

Metadata seed: `npm run db:instances:seed`. Он создаёт/обновляет metadata общих
инстансов. `npm run db:stage-one:seed` атомарно публикует Stage 1 с пользовательскими
таблицами Lab 78 и Fortress/Castle Dungeon, сохраняя рекомендации других инстансов.

Стадии управляются `node scripts/manage-server-stages.cjs <operation.json>`.
Пример создания draft (имена и номера служат примером формата, не выполняются seed):

```json
{
  "key": "server-stage-4-draft-import-001",
  "actor": "operator-name",
  "sourceLabel": "Таблица пользователя",
  "stage": { "code": "STAGE_4", "name": "Stage 4", "sequence": 4 },
  "recommendations": [],
  "confirmEmpty": true
}
```

Строка recommendations: `{ "instanceCode": "FREYA_HARD", "itemId": "точный-id",
"sortOrder": 0, "sourceMetadata": { "source": "название таблицы" } }`.
Ссылки должны указывать на активные общие Item/Instance; дубликаты запрещены.
Массив заменяет весь набор данной стадии атомарно. Пропущенный массив сохраняет
набор. Для существующей Stage требуется expectedRevision из БД. Пустой набор
требует явного confirmEmpty, а не считается автоматически готовым.

Публикация: stage + expectedRevision + `publish: true`; `isSelectable` опционален.
`current: "auto"` снимает явное назначение; `current: "STAGE_3"` назначает конкретную
опубликованную доступную стадию. При current=max публикация большего номера сразу
меняет default авто-групп. Чтобы подготовить новую публикацию, оставив прежний
current, в той же операции явно назначить прежнюю доступную Stage.

Отключение явного current требует одновременно перевести current на другую Stage
или auto. Override группы сохраняется и отображается как недоступный, вместо
тихого переключения. PublishedAt/code/sequence опубликованной Stage не откатываются.
Одинаковый key/файл повторяется без изменений, другой payload того же ключа запрещён.
Обновления опубликованных наборов увеличивают revision и записывают source/actor/diff
в ServerStageAuditEvent одной транзакцией. Прямой SQL оператора должен соблюдать
этот протокол, а не обходить его произвольным UPDATE.

## Миграция и транзакции

Миграция `20261106203000_instance_catalog_stages` выполняется в BEGIN/COMMIT.
Добавляет таблицы каталогов/стадий/пресетов и nullable поля Party/Item/Raid.
Сначала создаётся partial global unique Item, затем удаляется прежний универсальный
index. Старые Item, LootDrop, snapshots, денежные поля и ID не преобразуются.
Новые nullable ссылки у старых рейдов остаются null. Глобальная конфигурация
создаётся с current=auto, но без выдуманной опубликованной Stage.

Дополнительные ограничения поддерживаются в `prisma/catalog-constraints.sql`.
`db:deploy` и production build применяют оба набора guards и metadata seed.
Production build запускает миграции автоматически: push с миграцией в master
является её применением к production. Перед публикацией проверяют SQL и резервную копию.

Общий порядок блокировок: shared stage advisory lock → party advisory lock → Raid
FOR UPDATE для edit. Административная публикация использует exclusive stage lock.
Ручная продажа, edit, сброс группы и Telegram используют один party lock; Telegram
держит его на всё уведомление. Финансовые веса и алгоритм распределения не меняются.
До применения migration нужен свежий backup/точка восстановления PostgreSQL и
проверка на отдельной Neon-ветке. Возврат старого приложения после появления
одноимённых private Item несовместим с прежней уникальностью; нужен совместимый
rollback build или forward fix, а не удаление новых данных.
