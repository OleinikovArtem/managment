# План улучшений UI/UX Party Bank Manager

## 1. Область и основания

План по `prompts/улучшения.md`. Реализация начинается только после подтверждения
пользователем этого документа. Здесь описано предлагаемое поведение; текущие правила
продукта до реализации остаются в `PROJECT_SPEC.md` и `docs/UI_RULES.md`.

Изучены `docs/PROJECT_CONTEXT.md`, относящиеся к задаче части
`docs/ARCHITECTURE.md`, `PROJECT_SPEC.md`, `docs/UI_RULES.md`, исходники форм,
Server Actions, repositories, Prisma relations и PostgreSQL guards. Проверены
существующие тесты сброса и контракты профессий, профилей и предметов.
Для Server Actions прочитан установленный Next.js guide
`node_modules/next/dist/docs/01-app/01-getting-started/07-mutating-data.md`.
Перед изменением маршрутов и cache API необходимо дополнительно читать соответствующие
локальные guides установленной версии.

Доказательства аудита: **source** — прочитанный код и документация.
Браузер, DOM, скриншоты и проверки доступности в runtime на этом этапе не запускались;
визуальные дефекты и успешность сценариев по ним не утверждаются. БД не изменялась.
Внешние сервисы и передача кода/данных не требуются. Изменённый до начала работы
`.gitignore` не относится к задаче и должен быть сохранён без вмешательства.

## 2. Текущее состояние и найденные проблемы

Приоритеты: P1 — существенная недоступность сценария; P2 — неудобство или пробел
состояний; P3 — визуальная полировка. Потенциальные риски ниже отделены от уже
наблюдаемых по коду проблем.

| Приоритет | Наблюдение (source) | Влияние и решение |
| --- | --- | --- |
| P1 | `PayoutList` при закрытии обнуляет `activeId` и размонтирует `PaymentForm`; сумма, дата, комментарий и ref ключа запроса принадлежат форме | Черновик теряется. Отделить открытость панели от выбранного получателя и хранить черновики по получателю |
| P3 | У `SidePanel` нет переходов открытия/закрытия | Добавить лёгкую CSS-анимацию с сохранением узла до конца закрытия |
| P2 | В составе native select предлагает базовый профиль и существующие профили; `ProfilePicker` рейда отдельно показывает Main/Subclass | Нет поиска и остальных профессий. Общий combobox с единым построением вариантов |
| P1 | `MemberProfileManager` уже имеет редактирование, но `member-manager.tsx` показывает его только при `profiles.length > 4` | Редактирование названия, роли и заметки обычного профиля недоступно через этот UI. Открыть существующий сценарий для обычных профилей |
| P2 | Update профиля не переводит уникальный конфликт Prisma в ожидаемую ошибку; нет версии редактируемой записи | Возможны необработанный конфликт имени и перезапись устаревшей формы. Добавить обработку ограничений и проверку версии |
| P2 | Удаления используют смесь `window.confirm`, `EditorDialog` и прямых вызовов actions | Неодинаковая защита. Общий confirmation dialog с pending/error и серверными ограничениями |
| P3 | `.raid-date-heading::before` и `::after` рисуют линии | Удалить локальные декоративные правила, сохранить текстовую иерархию |
| P2 | `/settings` последовательно выводит группу, Stage, ссылки, блок бэкапов и Reset; Telegram расположен отдельно | Организовать три вкладки, переиспользовать реальные формы и правила доступа |
| P2 | Reset уже выбирает категории, раскрывает зависимости и требует ручную фразу; предпросмотр перечисляет категории, но не количества записей | Сохранить механизм, добавить серверный предпросмотр объёма удаления |
| P2 | `ItemForm` использует текстовый ранг, поля `itemSubtype` и `gameVersion` | Заменить ранг на фиксированный список, скрыть два поля без потери их значений |

Текущие важные ограничения:

- Main — `PartyMember.className`, Subclass — активные `PartyMemberProfile` со
  `subclassSlot` 1–4; есть legacy-профили без слота. Ссылки используются составами
  и историческими рейдами. Разделение в БД сохраняется.
- Слот `PartyCompositionMember` хранит `memberId` и nullable `profileId`, но не
  произвольную профессию. Вход рейда также принимает `profileId`; сервер сам делает
  `classSnapshot`. Одного изменения select недостаточно.
- Уникальны имя профиля внутри персонажа и номер subclassSlot; профиль
  отключается, исторические ссылки сохраняются. Создание ограничено четырьмя
  активными профилями, legacy-данные нельзя автоматически чистить.
- Обычное удаление состава запрещено, если на него ссылается рейд. Текст диалога
  должен объяснять запрет; разрешённое удаление через Reset — отдельный сценарий.
- `Item.grade`, `itemSubtype`, `gameVersion` — nullable строки. Update repository
  превращает отсутствующие `itemSubtype`/`gameVersion` в `null`: скрытие формы без
  изменения контракта обновления уничтожит метаданные.

## 3. Предлагаемые изменения

### 3.1. Финансы: панель передачи Adena

Переиспользовать `SidePanel` и Base UI. Анимировать opacity backdrop и
opacity/translate панели примерно за 160–220 мс. Панель остаётся fixed overlay;
анимировать высоту страницы не требуется. Учитывать состояния начала/конца
перехода установленного Base UI, `prefers-reduced-motion`, scrollbar и focus return.
Родитель не должен размонтировать панель до окончания exit transition.

Черновики суммы, даты, комментария и его раскрытия хранить в памяти страницы по
`memberId`, независимо от открытости. Сохранять ключ идемпотентности для неизменённого
запроса после сетевой ошибки. После успешной записи удалять только черновик
получателя; новый черновик использует существующий prefill. Закрытие, Escape,
backdrop и переключение получателей не теряют ввод. Во время отправки закрытие
блокируется. При обновлении остатков показывать свежую сводку, введённую сумму
не пересчитывать автоматически. Между группами черновики не переносить.
Перезагрузка страницы и уход из раздела не входят в обещание сохранения черновика;
localStorage с финансовыми данными не добавлять.

**Файлы:** `src/components/ui/side-panel.tsx`,
`src/features/sales/payout-list.tsx`, `src/features/sales/payment-form.tsx`,
`src/app/globals.css`; при необходимости отдельный модуль состояния черновика в
`src/features/sales/`. Payment actions/repository и денежный parser не менять.

**Готовность и проверка:** закрыть каждым способом и открыть повторно; перейти
между двумя получателями; проверить ошибку и повтор неизменённого запроса,
успешную отправку, обновление баланса, нулевой остаток и смену группы. Проверить
desktop/mobile, reduced motion, focus trap/return и отсутствие сдвига списка.
Существующие `payment-schema.test.ts`, `payment-repository.test.ts` и
`adena.test.ts` должны сохранить результат. Поведение черновика проверить в браузере.

### 3.2. Единый поиск профессии

Сделать общий компонент профессии на установленном Base UI Combobox и чистый
builder вариантов. Порядок: непустой Main, активные Subclass по слоту,
затем остальные профессии существующего каталога High Five по алфавиту.
Нормализация поиска и устранения дублей — trim и сравнение без учёта регистра.
При совпадении профессии Main имеет приоритет, затем первый профиль по стабильному
порядку слотов. Каждая профессия показана ровно один раз; совпадающие названия
из остальных вариантов каталога исключаются. Поиск сохраняет этот порядок.
По последнему уточнению пользователя участник имеет один игровой профиль с Main
и сабами: отдельные варианты сохранённых профилей одной профессии в списке не нужны.
Внутренние строки `PartyMemberProfile` и legacy-данные остаются в БД; они не образуют
дополнительную группу вариантов между сабами и каталогом. Их сохранённые ссылки
при открытии старого состава должны разрешаться без молчаливой замены или удаления.
Подписи могут пояснять источник, но отдельного переключателя
«Основная / Сабкласс» не будет. Текущий legacy-класс вне каталога не исчезает из
редактируемой формы. У персонажа без классов доступен весь каталог и пустое
значение; отсутствие результата поиска явно подписано.

Контракт выбора: Main, существующий Subclass либо профессия из каталога.
Выбор «остальной» профессии **не создаёт** профиль и не меняет Main/Subclass.
Это может быть профессия твинка участника: выбор принадлежит только конкретному
слоту конкретного состава. В другом составе тот же участник может иметь другую
профессию. Ни сохранение, ни редактирование состава, ни создание рейда из него
не изменяют профиль участника, его Main, сабы или их метаданные.
Для сохранённого состава добавить nullable `classOverride` в
`PartyCompositionMember` через аддитивную PostgreSQL migration. Старые строки с
`null` продолжают работать по `profileId`/Main. Для входа рейда добавить такой же
необязательный override; сервер валидирует разрешённую профессию и сохраняет её в
существующем `RaidParticipant.classSnapshot`. Новый столбец рейда предварительно
не нужен: чтение и edit должны уметь восстановить выбор из снимка.
Одновременные `profileId` и override запрещены. Профили проверяются на группу,
персонажа и активность сервером. Роль/уровень при override наследуются от
персонажа, `profileSnapshot` остаётся null. Override во входе рейда переносит выбор
состава в снимок конкретного рейда и не является настройкой профиля участника.

Создание → сохранение → повторное открытие и редактирование состава → создание
рейда → исторический просмотр → допустимое редактирование рейда сохраняют выбор.
Добавить отсутствующий сценарий редактирования сохранённого состава с загрузкой
его текущих слотов и обновлением по ID без создания дубликата. Изменение состава
влияет на будущие рейды; уже созданные рейды сохраняют свои снимки.
При редактировании исторический снимок не заменяется текущим классом
персонажа, если выбор не изменён. Заблокированный продажей рейд не получает новых
возможностей изменения состава. Идемпотентный hash создания учитывает override.

Компонент также использовать для полей профессии в формах участника и профиля;
четыре слота Subclass и Main в редакторе самого персонажа сохраняются как данные.
Локальный каталог содержит 37 имён High Five, включая Kamael. В рамках плана
«полный список» означает ровно этот поддерживаемый каталог; расширение до ранних
профессий не входит в задачу.

**Файлы:** новые `src/features/members/profession-select.tsx` и
`profession-options.ts`; `class-select.tsx`, `lineage2-classes.ts`,
`member-manager.tsx`, `member-profile-manager.tsx`;
`src/features/compositions/composition-manager.tsx`, `composition-schema.ts`;
`src/features/raids/raid-form.tsx` (uses shared `profession-select.tsx`),
`raid-schema.ts`; `src/server/repositories/composition-repository.ts`,
`raid-repository.ts`, `src/server/services/raid-service.ts`;
страницы `/compositions`, `/raids/new`, `/raids/[id]/edit` при изменении mapping;
`prisma/schema.prisma`, новая migration в `prisma/migrations-postgresql/`.
`src/app/(dashboard)/members/composition-actions.ts` — добавить обновление состава
по ID, проверку прав/принадлежности и актуализацию UI; repository и схема состава
должны поддерживать update без изменения исторических рейдов. Raid actions
затрагивать только для нового контракта ошибок/данных.

**Готовность и проверка:** Main первой строкой, затем сабы по слотам, затем
остальные 37 профессий за вычетом уже показанных по алфавиту; дубли Main/сабов/
каталога отсутствуют, legacy-ссылки не теряются. Пустые и
длинные значения, поиск разным регистром, очистка поиска, стрелки/Enter/Escape/Tab,
scroll списка на mobile. Проверить round trip override, старые составы без него,
отключённый/чужой профиль, повтор creationKey и заблокированный рейд. Unit tests
builder и схем: сортировка каталога, стабильный порядок при поиске, дедупликация
без учёта регистра, отсутствующие Main/сабы. Расширить `raid-service.test.ts`,
`raid-repository.test.ts` и `member-subclass.integration.test.ts`; добавить integration
создания и обновления состава с override. Отдельный сценарий: профессия твинка,
отсутствующая в профиле → сохранить → открыть и изменить состав → создать рейд →
изменить состав/профиль участника → проверить исходную профессию в истории рейда.
Сравнить Main, сабы и их метаданные до/после; они неизменны. Проверить независимые
override одного участника в двух составах и отсутствие дубликата состава при update.
Prisma validate и проверка аддитивной migration на заранее настроенной локальной
тестовой БД, указанной через `TEST_DATABASE_URL`. Новые тестовые БД автоматически
не создавать.

### 3.3. Редактирование игровых профилей

В интерфейсе это единый профиль участника с Main и сабами. Термин
`PartyMemberProfile` ниже обозначает существующие внутренние строки Subclass/legacy,
а не новую систему нескольких пользовательских профилей. Не добавлять отдельные
профили твинков: их профессии выбираются только в составе через `classOverride`.

Обеспечить редактирование единого профиля участника при обычном количестве сабов,
сохранив компактную карточку и меню действий. Переиспользовать существующие формы
и actions; `MemberProfileManager` адаптировать как внутренний редактор данных
сабов/legacy без предложения создавать отдельный пользовательский профиль.
Открывать текущие Main, сабы, роль и заметки; существующие названия внутренних
записей и скрытый уровень сохранять. Добавление саба остаётся в пределах четырёх
слотов редактора участника; legacy-данные остаются редактируемыми.
Не предлагать управление профилями неактивного персонажа.

Добавить ожидаемые ошибки уникального имени/слота, отсутствия или отключения
профиля. Для конфликта параллельного редактирования передавать исходный `updatedAt`
и сравнивать его внутри транзакции под существующей блокировкой персонажа.
При несовпадении не перезаписывать данные, сохранить форму и предложить загрузить
актуальную запись. Аудит писать только при успешном изменении. Обновление по ID
сохраняет ID, subclassSlot и исторические snapshots; новый профиль не создаётся.

**Файлы:** `src/features/members/member-manager.tsx`, `member-profile-manager.tsx`,
`member-profile-schema.ts`, `member-profile-action-result.ts`;
`src/app/(dashboard)/members/page.tsx`, `profile-actions.ts`;
`src/server/repositories/member-profile-repository.ts`. Новая миграция не нужна:
`updatedAt` уже существует. Проверить совместимость с `member-subclass-repository.ts`.

**Готовность и проверка:** редактирование единого профиля при 0–4 сабах и при
существующих >4 legacy-строках без добавления новых пользовательских профилей; дубликат имени,
пустые/слишком длинные поля, чужая группа, отключённый профиль, параллельная правка
и отключение, двойное сохранение, ошибка сети. Старый рейд сохраняет снимок;
новый получает актуальные данные. Добавить schema/action tests конфликтов и
расширить PostgreSQL integration профилей; визуально проверить форму на mobile.

### 3.4. Подтверждение опасных действий

последствия, «Отмена» и destructive-кнопка, pending, inline error, защита повторного
submit, удержание/возврат фокуса. Не закрывать на время запроса; после ошибки
сохранять контекст. Для отключения/архивации использовать точный глагол
«Отключить»/«В архив», чтобы не обещать физическое удаление.

### 3.7. Reset: граф зависимостей и предпросмотр

Существующий механизм сохраняется. `reset-plan.ts` используется UI и сервером:

```text
продажи → выплаты
лут → продажи → выплаты
рейды → лут → продажи → выплаты
участники/профили → рейды и составы → зависимые данные
составы → обнуление compositionId в рейдах, сохранение снимков и финансов
```

`PaymentAllocation` ссылается на выплаты и доли; `SaleShare` — на продажу,
участника рейда и персонажа; `LedgerEntry` — на транзакцию и персонажа.
Эти связи в основном RESTRICT. `PartyCompositionMember` имеет Cascade от состава,
но профиль и персонаж защищены Restrict. Поэтому независимое удаление профилей,
долей, отдельных проводок, оплаченного лута или аккаунтов не добавлять.

`party-repository.ts` уже удаляет покрытия, проводки, выплаты, доли, продажи,
лут и рейды в допустимом порядке; обнуляет ссылки на составы перед удалением
составов и удаляет профили перед персонажами. Операция использует Serializable,
party advisory lock, `FOR UPDATE Party`, локальный `app.party_reset` и до трёх
попыток. Сохранять эти защиты и SQL guards. При сбросе продаж снимается lockedAt,
лут становится RECEIVED, Telegram allocations очищаются, нерешённые импорты
становятся IGNORED; PROCESSED сохраняет защиту от повторного учёта.

Добавить read-only preview action только для OWNER и активной группы. Он использует
тот же resolver зависимостей и возвращает количества сущностей, долей, покрытий,
проводок, а также затрагиваемых Telegram-записей. Считать в согласованном snapshot,
показывать loading/error/пустой результат. При смене выбора сбрасывать подтверждение
и игнорировать запоздалый ответ предыдущего preview. Подписать автоматически
включённые категории и отдельно то, что сохранится: общий и собственный каталог,
аккаунты, группа, доступы, Telegram-конфигурация, aliases, inbox и аудит.

Предпросмотр — оценка на момент запроса, не блокировка группы до клика. Перед
выполнением сервер повторно проверяет доступ, выбор и зависимости; итоговый состав
данных может вырасти из-за параллельных операций, что нужно явно объяснить.
Контракт удаления строго показанного набора записей не вводится. Изменение количества записей после
preview само по себе не блокирует выполнение и не требует совпадения версии.

Сохранить текущие категории, автоматические зависимости, ручную фразу, полномочия
и атомарное выполнение. Весь редактор показать плоско на вкладке Reset: описание,
выбор, предупреждения, серверный preview и поле фразы непосредственно в странице.
Общий confirmation dialog использовать только для последнего подтверждения
действия с кратким итогом; не переносить туда категории, preview или ввод фразы
и не добавлять дополнительных шагов сброса. Изменение выбора/выход из вкладки очищает фразу.
Повторный submit блокировать. Новые категории и разрушительные миграции не нужны.

**Файлы:** `src/features/settings/reset-data-card.tsx`, `reset-plan.ts` (только
если нужен общий тип preview), `party-action-result.ts` либо отдельный preview type;
`src/app/(dashboard)/settings/actions.ts`,
`src/server/repositories/party-repository.ts` (добавление read-only preview).
`prisma/postgresql-constraints.sql` и `catalog-constraints.sql` — источники
ограничений, изменение защит не планируется.

**Готовность и проверка:** все непустые комбинации шести категорий и их замыкание;
ничего не выбрано; обязательную зависимость нельзя снять; preview меняется при
выборе и не принимает старый ответ. Недоступность БД блокирует подтверждение.
Проверить плоское представление без модалки выбора и текущую ручную фразу;
после успешного preview создать ещё одну затрагиваемую запись в тестовой группе:
показать предупреждение об актуальности, повторно проверить права и зависимости
при выполнении, завершить сброс по текущим данным без ошибки версии. Изменение
или отзыв прав после preview должно по-прежнему запрещать операцию.
Проверить роли, изоляцию групп, rollback при ошибке, сохранение каталога/доступов,
сброс только выплат и только составов, Telegram replay protection, параллельную
продажу/выплату и восстановление SQL guards после завершения транзакции.
Расширить `reset-plan.test.ts`, `reset-actions.test.ts`,
`src/server/repositories/party-reset.integration.test.ts` для preview и конкуренции.
Существующие integration tests уже проверяют выборочное и атомарное удаление.
Запускать на единственной заранее настроенной локальной PostgreSQL-БД через
`TEST_DATABASE_URL`. Не создавать новые БД и не выполнять тестовый Reset на рабочей
или production-БД.

## 5. Риски и неизменяемые правила

| Риск / зависимость | Мера |
| --- | --- |
| Произвольный класс не помещается в текущий контракт profileId | Аддитивный override, единый серверный resolver, тесты round trip и старых строк |
| Дубли профессий и существующие legacy-ссылки | Единый профиль с Main/сабами; список Main → сабы → каталог по алфавиту без дублей; legacy-ссылки сохраняются без изменения данных |
| Профессия твинка может случайно попасть в профиль или другой состав | Override принадлежит слоту состава, snapshot — рейду; тест независимых составов и неизменности Main/сабов |
| Одновременное редактирование профиля и четырёх слотов | Одна блокировка персонажа, проверка версии, конфликт вместо перезаписи |
| Ошибочная очистка скрытых metadata | Сервер сохраняет нетронутые столбцы; отдельные регрессионные tests |
| Сдвиги/потеря фокуса при анимации и unmount | Проверка lifecycle Base UI; overlay, exit transition, reduced motion и браузер |
| Preview устаревает и запросы приходят не по порядку | Snapshot, отмена устаревших ответов, явное предупреждение и серверная повторная проверка; без дополнительной блокировки по версии данных |
| Вкладки случайно открывают owner-only данные или теряют ввод | Серверные права на загрузку и actions; dirty-state поведение; никаких токенов в URL/storage |
| Build может загрузить production env | Перед build проверить scripts/build.cjs и конфигурацию, запускать с безопасной средой без операций записи |

Финансы неизменны: BigInt и десятичные строки; равные доли только PRESENT
исходного рейда; snapshot weights соответствуют исходным metadata; смысл чисел без
суффикса, multiplier, payment-prefill, FIFO и ключи идемпотентности сохраняются.
Новые UI-библиотеки не нужны. Типы строгие; бизнес-правила остаются в
services/repositories и общих схемах, не в компонентах представления.

## 7. Принятые решения и оставшиеся вопросы

- `classOverride` принадлежит слоту состава; допускает профессию твинка из каталога
  без создания профиля и без изменения Main/сабов. Сохраняется при редактировании
  состава и переносится в исторический снимок при создании рейда.
- Используется текущий каталог из 37 профессий High Five без расширения.
- Последнее уточнение пользователя определяет единый профиль участника с Main и
  сабами и список без дублей: Main, сабы по слотам, остальные по алфавиту.
  Более раннее предложение показывать несколько профилей одной профессии отдельными
  вариантами заменено этим правилом. Существующие legacy-данные не удаляются.
- Имя аккаунта находится во вкладке «Группа» с краткой подсказкой под полем:
  применяется ко всем группам и не является игровым никнеймом или логином.
- Reset сохраняет текущие правила в плоском виде на отдельной вкладке; серверный
  preview показывает количества, предупреждает об актуальности, выполнение повторно
  проверяет доступ и зависимости. Дополнительной проверки версии данных нет.

Нерешённых продуктовых вопросов по этим уточнениям нет. Проверка lifecycle Base UI,
mapping legacy-ссылок и SQL аддитивной migration остаётся технической частью
реализации и её проверок.
