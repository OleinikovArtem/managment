# Правила интерфейса

## Назначение

Интерфейс предназначен для ежедневной работы с рейдами, добычей и Adena.
Приоритет — понятная иерархия, быстрое внесение данных и читаемая история.
shadcn/Base UI и Tailwind — инструменты реализации, а не готовый визуальный шаблон.

## Визуальная основа

Источник токенов — `src/app/globals.css`, локальных правил Raid Detail —
`src/features/raids/raid-detail-view.css`.

| Назначение | Значение |
| --- | --- |
| Фон | `#101112` |
| Текст / вторичный текст | `#f0f1f2` / `#a8afb6` |
| Поверхность формы | `#17191b` |
| Разделитель / граница поля | `#2b3035` / `#68717a` |
| Focus | `#9ec5ff` |
| Ошибка | `#ff9898` |
| Акцент данных / Adena | `#e6be67` для акцента; Adena использует `hsl(45 92% 56%)` |
| Шрифт | Segoe UI, system-ui, системные fallback |

Обычный h1 — 24 px; Raid Detail использует 30 px на desktop и 24 px на mobile.
Основной текст — 14–16 px, вторичные метаданные — 12 px. Суммы используют tabular nums.
Цвет не заменяет текстовый смысл: долг, переплата, остаток и ошибка подписываются.

Содержимое ограничено 1280 px. Общие отступы — 16 px на mobile, 24 px на tablet,
32 px на desktop; секции разделяются пространством и тонкими линиями.
Поверхность нужна для ввода/редактирования или всплывающего контекста.
Не оборачивать каждую строку и метрику в карточку; не добавлять вложенные рамки,
декоративные градиенты, иконки или тени без функции.

## Навигация

Четыре основных раздела: Обзор, Рейды, Финансы, Группа. Лут, каталог и настройки —
отдельные вторичные пункты. Финансы объединяют маршруты выплат и операций;
Группа — участников и составы. Вложенная страница сохраняет активность раздела.

Desktop sidebar включается от 1024 px. Ниже — компактный header, четыре ссылки
и меню всех разделов. Мобильное меню использует доступный диалог с удержанием
фокуса, закрытием по Escape и возвратом к инициатору.

## Действия и раскрытие

- На странице одна ясная основная задача: создать рейд, добавить участника,
  записать продажу или передачу. Частые действия остаются подписанными и видимыми.
- Редактирование, отключение и редкие действия строки группируются в `ActionMenu`.
  Trigger виден постоянно, имеет доступное имя и работает с клавиатуры.
- История, доли, дополнительные фильтры и комментарии раскрываются по запросу.
  Не скрывать действия продажи/передачи в меню ради минимального вида.
- В одном workspace открыта одна форма продажи/передачи. Сворачивание и смена
  строки сохраняют черновик; успешная отправка очищает его и обновляет данные.
- Опасные действия отделены; очистка требует ручного подтверждения. Исторические
  финансовые данные не получают обычного действия удаления.

## Композиция экранов

| Экран | Иерархия |
| --- | --- |
| Обзор | Банк и остатки → последние рейды → раскрываемая аналитика |
| Raid Detail | Название/время → добыча с количеством и остатком → продажа и история; roster сбоку или ниже |
| Выплаты | Банк, начисления и переплаты → поиск/тип остатка → получатели и inline-передача |
| Операции | Поиск/тип → хронологический журнал → раскрытая точная сумма и доли |
| Участники | Поиск/статус → строки → раскрытые профили; editor профиля в диалоге |
| Составы | Выбор сохранённого состава → roster; отдельный builder |
| Каталог | Поиск/категория → количество результатов и добавление → строки и пагинация |
| Лут | Поиск/статус продажи → поступления от новых к старым → остатки, сумма продаж и ссылка на рейд |
| Настройки | Группа → резервные копии → закрытые опасные действия |

Списки сохраняют длинные названия и читаемую связь значения с подписью.
Не обрезать единственный источник важного имени или точной финансовой суммы.
Короткая сумма помогает сканировать список; полная доступна в деталях, а не только hover.

## Формы и состояния

У поля есть label, обязательность и понятная ошибка. Необязательные комментарии
и классификацию можно раскрывать. Некорректная дата остаётся видимой.
Не менять смысл денежного ввода, parser или prefill в рамках визуальной правки:
действует контракт из [PROJECT_SPEC.md](../PROJECT_SPEC.md#денежный-ввод).

Показывать pending, блокировать повторную отправку, сохранять введённые значения
при ошибке. Успех обновляет соответствующие страницы и остатки. Empty state
объясняет отсутствие данных и следующий доступный шаг; загрузка сохраняет
структуру страницы; ошибка предлагает повторить; отсутствующая запись — путь назад.
Не показывать сырые SQL/Prisma детали пользователю.

## Адаптивность и доступность

- Поля на узких экранах — минимум 16 px, touch controls — минимум 44 px.
- Учитывать доступную ширину контента. Raid Detail складывает колонки при ширине
  контейнера ≤800 px; отсутствие overflow само по себе не доказывает удобство.
- Сохранять читаемость длинных roster, нескольких поступлений, частичных продаж,
  больших сумм и переплат. Не превращать mobile в уменьшенную desktop-таблицу.
- Использовать semantic headings, labels, native details и `aria-current`.
  Видимый focus обязателен; состояние не передаётся только цветом.
- Поддерживать клавиатуру, Escape для диалогов, focus management и reduced motion.

## Проверка изменений

Для изменённого экрана снять и открыть desktop/mobile screenshots с одинаковыми
данными и viewport до/после. Оценить иерархию, плотность, отступы, текст, действия,
переносы и clipping. При найденной проблеме выполнить correction pass и переснять.

Проверять 1440/390 px для основных экранов, 320/768/1024 px для shell и сложной
композиции. Проверять клавиатуру, формы и доступность точных сумм. Не отправлять
тестовые продажи, выплаты или очистку на рабочей базе. Отдельно проверять empty,
loading, error, success и pending на безопасных данных.

Lint/build/tests дополняют визуальную проверку. Не заявлять WCAG-conformance,
проверку screen reader или поведенческих состояний без фактической проверки.
В постоянной документации хранить правила и ограничения, не историю итераций,
скриншоты прогресса или журнал одобрений.
