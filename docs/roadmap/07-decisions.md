# Решения, вопросы и ограничения плана

## Что уже определено пользователем

1. Реальные правила откатов/СА будут переданы позже таблицей. До этого допустимы mock-значения с привязкой к нашим инстансам.
2. Учёт ведётся по персонажу; сохранение рейда автоматически закрывает инстанс для PRESENT.
3. Сначала календарь с ручными отметками, потом связь с рейдами и групповые напоминания, позже личный бот. Денежные сведения — лично после подтверждённой привязки.
4. Рейды заранее не планируются: сохранённый рейд означает состоявшийся поход. Отдельный статус завершения не нужен; будущие даты не должны закрывать календарь заранее.
5. Личный бот требует аккаунт приложения: администратор назначает игроку одного или нескольких персонажей, игрок подтверждает Telegram-привязку.
6. Групповые напоминания включают всех активных персонажей без исключений, независимо от сохранённых составов.

## Архитектурные ориентиры для оценки задач

Это предлагаемые сущности, не готовая Prisma-схема:

| Сущность             | Основные связи и инвариант                                                                               |
| -------------------- | -------------------------------------------------------------------------------------------------------- |
| Правило отката       | Группа, instanceId/lockoutKey, revision, effectiveFrom, timezone; demo не публикуется как verified       |
| Источник закрытия    | Группа, персонаж, правило/revision, границы периода, время прохождения, raidId или manual, статус отмены |
| Правило СА           | Контекст сервера, instanceId, bossKey, переход уровня, условия, источник/revision                        |
| Назначение персонажа | partyId + memberId → userId; один активный владелец персонажа                                            |
| Telegram-привязка    | botId + Telegram user ID + назначение; pending/active/revoked, одноразовый challenge отдельно            |
| Подписка и задание   | Получатель, scope, период/окно, часть сообщения, статус доставки/lease; уникальные ключи                 |
| Отсутствие           | Группа, персонаж, UTC-интервал, исходная timezone, автор и ограниченно видимая заметка                   |

Наличие связи между персонажами разных групп автоматически не подразумевается: `PartyMember` scoped к группе. Даже если в игре это один персонаж, межгрупповая синхронизация — отдельный scope.

## Основания в текущем проекте

- [prisma/schema.prisma](../../prisma/schema.prisma): `PartyMember` не имеет владельца-аккаунта; `Instance` имеет стабильный code; в `Raid` есть occurredAt, instanceId, creationKey, снимки Stage и participants. Таблиц календарных закрытий/подписок сейчас нет.
- [prisma/seeds/instances.json](../../prisma/seeds/instances.json): 19 кодов инстансов, используемых для mock-связей. Это проверка seed-файла, не утверждение о содержимом работающей БД.
- [src/server/auth/party-access.ts](../../src/server/auth/party-access.ts): MEMBER читает, изменение требует ADMIN, некоторые операции OWNER. Self-service бота требует отдельной проверки владения.
- [webhook route](../../src/app/api/telegram/webhook/[webhookId]/route.ts), [import-service.ts](../../src/server/telegram/import-service.ts): текущий входящий поток ориентирован на продажи.
- [bot-api.ts](../../src/server/telegram/bot-api.ts): helper сейчас поддерживает методы настройки/проверки webhook, исходящую доставку сообщений нужно добавить.
- Правила денег и сброса: [ARCHITECTURE.md](../ARCHITECTURE.md), [PROJECT_SPEC.md](../../PROJECT_SPEC.md). В разделе каталога ACCOUNTS_AND_PARTIES_SPEC.md есть старое описание общего редактирования; оно не основание менять доступ к каталогу: актуальный scope проверяется в коде и PROJECT_SPEC.md.

## Граница достоверности

План проверяется на покрытие исходных идей, зависимости, согласованность терминов, права, жизненный цикл и тестируемую приёмку. Разработка приложения и миграции этим документом не выполнены. Игровые факты не проверялись: пользователь отложил их предоставление. Запуск UI, E2E и реальная отправка Telegram понадобятся при реализации каждого этапа.
