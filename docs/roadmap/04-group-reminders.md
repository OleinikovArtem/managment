# F04. Напоминания в Telegram-группу

Цель: отправить группе одно понятное сообщение перед откатом, если выбранные инстансы ещё не отмечены у активных персонажей. Без сумм Adena и без раскрытия данных другой группы.

## TG-01. Чат назначения и разделение Telegram-потоков — этап 3

**Описание.** Добавить исходящий чат напоминаний, сохранив существующий личный чат приёма пересланных продаж BOHPTS.

**Требования.**

- Чат назначения — отдельная настройка; существующий `PartyTelegramBotConfig.chatId` нельзя переиспользовать как чат напоминаний, он участвует в проверке источника импорта продаж.
- Рекомендуется существующий receiving bot группы. Отдельный бот — только если пользователь выберет это в Q5; второй webhook для того же токена не создавать.
- OWNER подключает/отключает исходящий чат и проверяет доступность тестовым сообщением. ADMIN/MEMBER не меняют токен или чат прямым запросом.
- Webhook маршрутизирует команды/привязку отдельно от импорта продаж, с сохранением проверки секрета. Обычные команды не создают `TelegramSaleImport`, не попадают в финансовый parser и не регистрируют продажи.
- В UI: не настроено, проверяется, готово, отключено, бот удалён/заблокирован, нет права отправки. Ошибки не содержат токенов, webhook-секретов или приватного payload.

**Приёмка / E2E.** OWNER задаёт тестовый чат, видит результат mock Telegram API, перезагружает настройки. ADMIN получает отказ. Пересланная продажа по-прежнему импортируется и сохраняет точные суммы; команда боту не создаёт продажу/inbox ошибки. Реальная доставка проверяется отдельно вручную с разрешённым тестовым чатом.

## TG-02. Правило «завтра откат» и состав сообщения — этап 3

**Описание.** Настроить одно ежедневное сводное сообщение по подтверждённым правилам календаря.

**Требования.**

- Предложение: время отправки 20:00 в timezone расписания группы; «завтра» — следующий календарный день в этой timezone, а не следующие 24 часа. Значение редактируемое; требует ответа Q3.
- Настройка включает выбранные инстансы; roster — все активные персонажи группы без исключений. Отдельный список персонажей, исключения для запасных и ограничение сохранённым составом не нужны. Деактивированные персонажи не включаются.
- В сообщение попадают все активные персонажи без действующего закрытия в периоде, заканчивающемся завтра. Инстанс без таких персонажей исключается; пустая сводка не отправляется.
- Текст: название группы, инстанс, точный откат/timezone, ники «нет отметки о прохождении», ссылка на календарь. Нет утверждения, что игра проверена ботом.
- Если до отправки рейд закрывает инстанс, набор пересчитывается. Demo и неизвестные правила никогда не используются реальным отправителем.
- Длинный список разбивается с сохранением понятной принадлежности частей. Telegram-разметка экранируется, ники не ломают сообщение.

**Приёмка / E2E.** При фиксированном времени один закрытый и один незакрытый персонаж дают сообщение только о втором. Проверить откат после полуночи, weekly, разные timezone браузера и сервера, полностью закрытый roster, отключённую настройку и demo. Изменение настройки сохраняется; MEMBER не меняет её.

## TG-03. Доставка, планировщик и повторы — этап 3

**Описание.** Добавить защищённый запуск фоновой отправки и устойчивый журнал заданий в существующем PostgreSQL. Конкретный механизм расписания выбрать при реализации под действующий хостинг.

**Требования.**

- Уникальность задания: группа + назначение + правило/период + окно отправки + часть сообщения. Параллельные запуски не создают два логических задания; claim/lease защищает от двух отправителей.
- Статусы минимум pending, processing, sent, retry, failed, unknown. Нужны время последней попытки, безопасный код причины и число попыток; повтор с ограниченным backoff.
- Успешно отправленные части повторно не отправляются. Retry после временного отказа перепроверяет настройки, актуальность периода и наличие незакрытых участников. После самого отката просроченное напоминание не отправляется.
- Таймаут после возможной отправки нельзя объявлять гарантированным отсутствием доставки. Telegram и локальная БД не дают общей транзакции: exactly-once внешнего сообщения не обещается. Рекомендация для unknown — без слепого автоповтора, решение доступно OWNER.
- Смена/отключение чата или бота отменяет старые ожидающие задания; нельзя отправить накопленные сообщения новому получателю. Секрет защищает scheduler endpoint, ручной запуск требует OWNER.
- Планировщик выбирает все наступившие, ещё не истёкшие задания, а не только совпадение с минутой запуска. После перезапуска обрабатываются пропущенные окна до самого отката; зависший processing освобождается по lease. Истечение периода отменяет остаток многочастного сообщения.
- OWNER видит статус последней отправки и причину недоставки; запрет отправки не ломает приём продаж.

**Приёмка.** Интеграционные проверки с fake Telegram API: два scheduler одновременно, 429/временный отказ, постоянный отказ, потеря ответа, сбой между send и сохранением sent, несколько частей, сброс группы. E2E проверяет видимый статус/повтор и сохранённую конфигурацию. Синтетические проверки не считаются подтверждением доставки в настоящий Telegram.

**Не входит.** Произвольные рассылки, баланс в групповом чате, нагнетание уведомлений каждый час, платные внешние очереди без отдельной необходимости.
