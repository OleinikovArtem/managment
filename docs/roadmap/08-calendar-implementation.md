# План реализации календаря на shadcn

Основание: [F01 — требования календаря](01-calendar.md), [общий roadmap](README.md), [UI_RULES.md](../UI_RULES.md). Первый результат — работающий `/calendar` с демонстрационными расписаниями, сохранёнными ручными отметками и компонентами shadcn. Автозакрытие от рейдов — следующий этап F03; Telegram и справочник СА сюда не входят.

План включает миграцию **всех интерактивных общих компонентов, которые календарь переиспользует**, включая оболочку приложения. Миграция меняет общую реализацию для существующих потребителей, а не создаёт отдельные копии компонентов для календаря. Изменение финансовой логики, числового ввода и prefill не допускается.

## 1. Технические решения

- Сохранить текущую конфигурацию `components.json`: shadcn `base-nova`, Base UI, neutral tokens, Tailwind 4, Lucide. Не запускать повторный init и не переключать проект на другой набор примитивов.
- Использовать существующие shadcn Button, Input, Textarea, Badge, Card, Separator, Sonner; адаптировать размеры календарных контролов к touch 44 px. Переписывать их только ради повторного получения из registry не требуется.
- Недостающие компоненты добавлять из совместимого Base UI registry shadcn с просмотром diff каждого файла. Не применять массовый overwrite к `src/components/ui`. Новые зависимости — только необходимые для выбранных компонентов, с обновлением lockfile.
- shadcn Calendar используется как **выбор даты** внутри DateInput. Сам календарь откатов — предметный список/матрица, его нельзя подменить обычным месячным date picker.
- Сохранить общий внешний API текущих DateInput, InstancePicker, EditorDialog, ConfirmationDialog, SidePanel и ActionMenu, где это возможно. Это адаптеры над shadcn, а не место для собственной реализации focus trap, listbox или управления portal.
- Чтение — server page → service/repository; изменение — Server Action → проверка сессии/роли → Zod → service → repository/транзакция. Часы и вычисление периодов передаются явно в чистые функции.
- Сохранить потоковую загрузку оболочки и проверку доступа. Клиентскими становятся фильтры/формы/локальный countdown, а не вся страница или layout. Следовать установленным Next.js docs и существующим `Suspense`/`await io()` паттернам проекта.

## 2. Состав экрана

`/calendar`: заголовок «Календарь инстансов», видимая метка demo и timezone, затем фильтры и список ближайших семи дней. Отдельное открытие истории не должно превращать ближайшие периоды в месячную сетку.

- Фильтры: инстанс, персонаж, «Ещё не закрыто»; сброс одним действием. Состояние в URL, восстановление при reload/back. Фильтр персонажа влияет только на просмотр, не исключает его из будущих групповых напоминаний.
- По умолчанию — все активные персонажи группы; инстансы с mock-правилами и остальные доступные инстансы со статусом «Нет правила». Не выдавать отсутствие правила за доступность или закрытие.
- Desktop: секции по ближайшему откату с компактной таблицей персонажей/статусов. Mobile: список инстансов с раскрытием персонажей. Смысл и действия одинаковы, горизонтальная прокрутка не обязательна для выполнения задачи.
- Инстанс показывает название, следующий откат, timezone, относительное время, число закрытых/активных персонажей. Персонаж — «Закрыто»/«Не отмечено», источник, время и доступное действие.
- Детали/история — SidePanel на shadcn Sheet. Ручная отметка — EditorDialog, выбор нескольких персонажей через Checkbox, дата и время через DateInput, необязательный комментарий. Отмена отметки — ConfirmationDialog с обязательной причиной в форме перед подтверждением.
- OWNER/ADMIN отмечают и отменяют; MEMBER видит историю без изменяющих действий. Сервер отклоняет поддельный запрос независимо от UI.
- На границе периода список обновляется по серверным данным; возврат фокуса во вкладку также обновляет просроченный snapshot. Локальный countdown не является источником статуса. При ошибке обновления показать устаревание, не рисовать выдуманное новое закрытие.

InstancePicker извлечь в `features/instances/instance-select.tsx`, чтобы календарь не импортировал UI из features/raids; старый экспорт временно оставить совместимым адаптером либо одновременно обновить оба места. Календарному фильтру «Все инстансы» задать явный внешний вариант: он не означает рейдовое «Без инстанса».

Для выбора персонажей использовать общий feature-компонент `features/members/member-select.tsx` на shadcn Combobox, для массового выбора — Checkbox. Не переиспользовать редактор профессии как выбор персонажа.

Новые примитивы по потребности: Combobox, Popover, Calendar, Dialog, AlertDialog, Sheet, DropdownMenu, Checkbox, Table, Skeleton, Alert, Field/Label, Sidebar и его необходимые зависимости. Не добавлять всю библиотеку заранее. Native layout/текст/Next Link остаются семантическими элементами; шадснизация не означает замену каждого div компонентом.

SectionNavigation сейчас не требуется `/calendar`: экран самостоятельный. Если при реализации его добавляют или извлекают ещё один существующий общий виджет, он также включается в миграцию и регрессионную проверку. Не оставлять рядом второй самодельный аналог реально используемого интерактивного компонента.

## 4. Пакеты реализации и зависимости

### IMP-01. Зафиксировать базовое поведение и добавить примитивы

Прочитать актуальные Next.js guides перед кодом. Проверить local DB URL, доступность двух групп/ролей через существующие fixtures. Снять исходные desktop/mobile состояния затрагиваемых общих компонентов; credentials и артефакты оставить вне Git. Добавить только примитивы для следующего пакета, сверяя актуальную документацию shadcn Base UI.

**Выход:** совместимые примитивы, список реальных импортов/потребителей и обновлённые E2E-сценарии, если добавляется видимый стенд/меняется поведение. Самостоятельный production showcase не нужен.

### IMP-02. Перевести общие виджеты и оболочку на shadcn

Порядок: Dialog/AlertDialog → Sheet/DropdownMenu → DateInput/InstancePicker/выбор персонажа → Skeleton → Sidebar и видимые элементы уведомлений. Удалять CSS старых виджетов только после проверки всех ссылок; не затрагивать общие токены и классы, используемые другими экранами.

**Выход:** карта из раздела 3 реализована, API/поведение существующих форм сохранены; dropdown → confirmation → finalFocus работает, popover даты внутри диалога не закрывает родительскую форму. Выплаты сохраняют отдельный черновик на каждого получателя и прежний prefill. Sidebar остаётся потоково загружаемым и доступным клавиатурой.

**Проверки:** обновить затронутые `e2e/raids.spec.ts`, `financial.spec.ts`, `mobile-keyboard.spec.ts`, `network-recovery.spec.ts`, `account-settings.spec.ts`, `workspace.spec.ts` и профильные проверки меню/подтверждений по реальным изменениям. Не переписывать ожидания ради нового DOM без проверки прежнего результата.

### IMP-03. Реализовать модель расписаний и расчёт периодов

Зависит от CAL-01, не от визуальной миграции. Предлагаемые файлы: `features/calendar/calendar-schema.ts`, `server/services/instance-reset-schedule.ts`, `server/repositories/calendar-repository.ts`, отдельная проверенная миграция для новых сущностей в принятой PostgreSQL-структуре проекта.

- Хранить scoped к группе настройки отслеживаемых инстансов и revision правил с effectiveFrom, timezone, типом daily/weekly, localTime/days, demo/verified. Источник закрытия хранит memberId, lockoutKey, revision и UTC-границы своего периода; несколько источников допускаются.
- Для подтверждения источника/отмены предусмотреть version, request key, автора, причину и связь с будущим raidId. Пока рейдовые источники не создаются.
- Композитные связи/ограничения обеспечивают принадлежность одной группе. Не делать каскад в существующие финансовые сущности и не пересоздавать каталог.
- Сейчас timezone mock — Europe/Kyiv; конфигурация группы и полномочия OWNER приняты как временные проектные решения из Q2/Q3, без выдачи их за правила реального сервера. Пока нет таблицы — не публиковать verified, не строить отдельный полный редактор расписаний.
- Расчёт `[start,end)` делается в timezone правила; DST требует детерминированной политики, без молчаливого сдвига. Неизвестные/неподдержанные правила остаются неизвестными. Если существующих средств Intl недостаточно для корректной реализации, отдельно выбрать минимальную зависимость на этапе кода, без самодельной арифметики UTC offset.

**Выход:** чистый сервис возвращает точные периоды на заданном now; unit-тесты покрывают границы, weekly, смену даты, DST и revision. Миграция не меняет финансовую семантику, ограничения Item и существующие данные.

### IMP-04. Подключить mock к существующим инстансам

Контролируемый идемпотентный загрузчик читает только resetRules из `mock-data.json`; soulCrystalRules здесь не используются. По code ищется global-or-own Instance; отсутствующий код — ошибка preview без создания новой записи. Уровень mode/timezone/effectiveFrom нормализуется в явные поля записей.

Применение требует выбранной группы и режима demo, не выполняется автоматически при запуске приложения/создании группы. Preview не пишет данные. Повтор применения не создаёт новые revision без изменения payload. Реальная таблица позже проходит тот же контракт; UI не зависит от JSON-файла напрямую.

**Выход:** шесть mock-правил связаны с реальными instanceId выбранной тестовой группы, другие инстансы честно показаны без правил. Другая группа не получает эти настройки. Внешних отправок нет.

### IMP-05. Чтение и экран `/calendar`

Зависит от IMP-02–04. Файлы: `app/(dashboard)/calendar/page.tsx`, `loading.tsx`, `error.tsx`, feature-компоненты `calendar-view.tsx`, `calendar-filters.tsx`, `calendar-details.tsx`, `calendar-skeleton.tsx` и модель представления.

Сервер авторизует группу, загружает только её записи и доступные инстансы/персонажей. DTO содержит ISO/decimal strings и nextResetAt/serverNow, не Prisma-объекты в client props. Клиент вычисляет только представление и countdown. Не показывать календарь чужой группы из cache; при смене группы старый snapshot/черновик не переносится.

Добавить календарь в shadcn Sidebar, обеспечить прямую ссылку и active-state. Из списка рейдов достаточно ссылки в календарь; синхронизация рейда не добавляется попутно.

**Выход:** фильтры, empty/no-rule/demo/loading/error/read-only, история и переход периода видны в браузере; reload/back сохраняют выбор. Время браузера не меняет периоды сервера.

### IMP-06. Ручное закрытие, отмена и сохранение

Зависит от IMP-03–05. Файлы: `app/(dashboard)/calendar/actions.ts`, `server/services/calendar-service.ts`, repository и формы в features/calendar.

- ADMIN выбирает инстанс, персонажей и прошлое/текущее время. Сервер проверяет роль, группу, активность, правило для времени события, набор без дублей и отсутствие будущей даты.
- Запись массовой отметки атомарна; request key с прежним payload возвращает результат, другой payload конфликтует. Сетевой retry сохраняет ключ и черновик.
- Отмена требует причины и version; отменяет конкретный источник. Итог закрытия — наличие любого действующего подтверждения. Отмена повторно безопасна, история остаётся читаемой.
- В первом релизе ручные отметки не создают Raid, LootDrop или финансовые записи.
- Новые FK должны совместно работать с уже существующим reset участников: расширить текущий preview и транзакцию очистки зависимых календарных записей. Настройки расписаний/каталоги сохраняются, сброс продаж/выплат на закрытия не влияет. Это требуется до первого выпуска persisted-отметок, не откладывается целиком до F03.

**Выход:** пользователь видит сохранённый результат после reload, отказ доступа и ошибка валидации ничего не пишут; конфликт не теряет ввод. Сброс тестовых участников остаётся работоспособным.

### IMP-07. Проверить весь сценарий и обновить текущие спецификации

Добавить `e2e/calendar.spec.ts` с существующими fixtures и Chromium. Проверять результат пользователя и persisted записи, а не один heading/HTTP 200:

| Сценарий          | Обязательная проверка                                                                      |
| ----------------- | ------------------------------------------------------------------------------------------ |
| Чтение/фильтры    | Две группы, одинаковые инстансы, разные отметки; reload/back; нет утечки                   |
| Массовое закрытие | Два выбранных персонажа закрыты, третий нет; точный период/источник в БД                   |
| Отмена/история    | Причина сохранена; второй источник оставляет статус закрытым                               |
| Права             | MEMBER читает, прямое изменение запрещено; ADMIN не меняет OWNER-настройки                 |
| Валидация         | Будущее/некорректное время, чужой персонаж, нет правила, деактивация, устаревшая version   |
| Сеть/конкуренция  | Потерянный ответ и повтор без дубля; две вкладки не затирают источники                     |

| Общие компоненты  | Рейд → продажа → выплата: прежние точные суммы, ввод и prefill; диалоги/меню/даты          |

Для проверки отката не ждать реального времени: передать часы в сервис и фиксировать тестовые расписания; управление серверными часами не должно стать публичным API. Browser clock сам по себе не управляет серверным расчётом.

Снять и открыть desktop/mobile screenshots календаря и затронутых общих экранов до/после; проверить 1440/390 px, shell/сложные композиции также 320/768/1024 px. Проверить empty/loading/error/long names, scroll панелей и popover поверх dialog/sheet. Исправить найденное и переснять.

Запустить lint, typecheck, unit-тесты и соответствующие integration checks в заранее настроенной локальной тестовой БД, затем affected E2E и полный Chromium до коммита фичи. Build запускать с проверенной средой: локальная production-сборка может подключаться к живой БД; не выполнять тестовые изменения через неё. Проверки форматирования включают добавленные файлы UI и календаря. Данные локальных сценариев остаются тестовыми; Item не очищается.

Обновить PROJECT_SPEC.md, ARCHITECTURE.md, PROJECT_CONTEXT.md, UI_RULES.md при изменении общих соглашений. Отчёт в ответе должен различать выполненные проверки и ограничения; текущий документ не утверждает, что реализация или тесты уже выполнены.
