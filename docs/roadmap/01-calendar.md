# F01. Календарь откатов инстансов

Цель: руководитель видит, у каких персонажей инстанс ещё не закрыт и сколько осталось до отката. Участник читает тот же календарь своей группы.

## Пользовательский сценарий

Пользователь открывает календарь → выбирает инстансы/персонажей → видит ближайший откат и статусы текущего периода. ADMIN отмечает внешнее прохождение персонажа без создания фиктивного рейда. В момент отката начинается новый период, предыдущие отметки остаются в истории. Также персонаж учасника может пройти рейд отдельно самостоятельно - мы это не учитываем, для пати это выглядит как пропуск

## CAL-01. Правила откатов и формат данных — этап 0

**Описание.** Добавить независимые от дропа правила расписания, связанные с `Instance.code`; при сохранении разрешать код в существующий `Instance.id` с проверкой global-or-own. Не создавать второй каталог инстансов.

**Требования.**

- Первое покрытие: фиксированное ежедневное и недельное расписание в IANA timezone. Интервал от прохождения резервируется в формате как неподдержанный тип; его реализация определяется таблицей пользователя.
- Поля: instanceCode, revision, effectiveFrom, timezone, тип, локальное время, дни недели для weekly, источник, признак demo/verified, ссылка на общий lockoutKey при необходимости.
- Правила относятся к группе и её конфигурации сервера. Не изменять общие инстансы ради расписания одной группы. Возможную связь со Stage определить по Q2.
- Текущий период — полуинтервал `[предыдущий откат, следующий откат)`. Прохождение ровно в откат относится к новому периоду. UTC хранится, серверная timezone управляет откатом; локальная timezone браузера — только представлением с явной подписью.
- Изменение правила создаёт новую revision с датой вступления. История сохраняет применённую revision/границы периода; новая настройка не пересчитывает историю молча.
- Нельзя рассчитывать историческое закрытие по сегодняшнему правилу, если для даты события нет действующей revision. Смена правила посреди текущего периода требует preview затронутых отметок; безопасное предложение — вступление с ближайшего отката.
- Неизвестное правило означает «Расписание не задано», а не ежедневный откат. Некорректная timezone/день/дата/дублирующиеся записи дают ошибку без частичного сохранения.
- Предложение до ответа Q2: расписание настраивает OWNER; ADMIN управляет только закрытиями. Реальную таблицу сначала сопоставить с кодами, показать preview добавлений/замен/неизвестных строк, затем применить атомарно. Формат файла и пользовательский upload не входят в первый релиз; контролируемого импорта достаточно.
- Demo полностью отделено от подтверждённых правил и не участвует в реальной отправке уведомлений. Неизвестный код не создаёт инстанс автоматически.

**Приёмка.** На фиксированных часах daily/weekly возвращают точные UTC-границы; за секунду до отката и в сам откат периоды различаются. Смена timezone браузера не меняет закрытия. Два редактора не затирают revision друг друга. Несуществующее/двойное время DST обрабатывается явно выбранной политикой (Q3), до этого такое правило не публикуется.

**Проверки.** Unit: границы суток/недели, несколько дней weekly, DST, revision. Интеграционные: уникальность, чужой instanceId, атомарное применение набора. E2E при появлении настроек: отказ MEMBER/ADMIN по принятой политике, сохранение, конфликт версии, неизвестный код.

## CAL-02. Экран календаря — этап 1

**Описание.** Показать ближайшие периоды и матрицу «инстанс × персонаж». Первый вариант — список по текущим периодам и ближайшим семи дням; месячная сетка не нужна для MVP.

**Требования.**

- Фильтры: инстанс, активный персонаж, «ещё не закрыто». По умолчанию показываются активные персонажи и выбранный набор отслеживаемых инстансов группы.
- Статусы: «Закрыто», «Не отмечено», «Нет правила». «Не отмечено» означает отсутствие записи в приложении, а не доказанное отсутствие прохождения в игре.
- Закрытие показывает время, источник «вручную/рейд», автора или ссылку на рейд. Время отката и обратный отсчёт не расходятся; после отката данные обновляются без необходимости повторного входа.
- Предлагаемый маршрут `/calendar`; ссылка из рейдов и карточки инстанса. Конечное размещение согласовать с навигацией проекта.
- Demo-баннер виден постоянно, включая детали и пустые результаты. Нет правил → объяснение и действие для OWNER; нет прав → только чтение.

**Приёмка / E2E.** Фильтры сочетаются; закрытый персонаж исчезает из «ещё не закрыто»; после перезагрузки результат тот же. В новом периоде снова «Не отмечено», история старого доступна. MEMBER читает, но прямой запрос изменения отклоняется. Данные другой группы не видны. Mobile и клавиатура позволяют открыть детали и вернуться к списку.

## CAL-03. Ручные отметки и исправления — этап 1

**Описание.** ADMIN/OWNER отмечают внешнее прохождение выбранных персонажей с временем и необязательным комментарием.

**Требования.**

- Закрытие привязано к `partyId + memberId + lockoutKey + периоду`; Main/Subclass не создают отдельные откаты без подтверждённых серверных правил.
- Будущее время отклоняется; прошлое попадает в свой исторический период, а не обязательно в текущий. Для архивного персонажа новые ручные отметки запрещены, существующие видны в истории.
- Можно отменить ошибочную отметку с причиной. Сохранять автора, время, предыдущий результат; не удалять историю исправлений.
- Отметки от рейда и ручные источники независимы. Удаление одного источника не открывает инстанс, если осталось другое действующее подтверждение.
- Повтор запроса не создаёт дубль; параллельные изменения дают определённый результат/конфликт. Для массовой отметки выбранных персонажей — одна атомарная операция.

**Приёмка / E2E.** Отметить двух персонажей → перезагрузить → увидеть закрытие только у них и в нужном периоде. Отмена одного ручного источника сохраняет закрытие от рейда. Неверная дата, будущее время, чужой персонаж и MEMBER не меняют данные. Повтор после потерянного ответа не создаёт второй источник.

**Не входит.** Самостоятельные отметки MEMBER, планирование времени похода, автоматическое получение игрового lockout. Правила ручных исправлений после появления рейдовой синхронизации уточняет F03.
