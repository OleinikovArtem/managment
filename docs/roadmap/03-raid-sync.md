# F03. Автоматическое закрытие по рейду

Подтверждённое требование: сохранение рейда автоматически закрывает выбранный инстанс для каждого PRESENT персонажа. Ручное подтверждение закрытия при каждом сохранении не требуется.

## RAID-01. Создание рейда и отметок одной операцией — этап 2

**Описание.** Встроить регистрацию источников закрытия в существующий путь сохранения рейда, посещаемости и добычи.

**Требования.**

- Период определяется по `Raid.occurredAt`, а не по времени нажатия «Сохранить». Запись прошлого рейда не закрывает текущий период автоматически.
- Использовать конкретный `instanceId`, снимок PRESENT и действующую для времени события revision правила. ABSENT не получает закрытие.
- Создание рейда и связанных отметок атомарно. Повтор `creationKey` с прежним payload возвращает тот же результат без новых источников; другой payload конфликтует по существующему контракту.
- Если правила нет, рейд сохраняется по текущим требованиям приложения; интерфейс сообщает «Календарь не обновлён: нет расписания». Никаких выдуманных периодов. Позднее восстановление отметок — через отдельный preview (RAID-03).
- Рейд без конкретной связи `instanceId` не сопоставляется по свободному названию. Есть понятное объяснение, почему синхронизации нет.
- По ответу пользователя рейд означает состоявшийся поход; планирование и отдельная кнопка завершения не нужны. Если в существующих данных/форме встретится будущее время, оно не закрывает календарь заранее: показать причину отсутствия синхронизации. Не добавлять фонового «завершения» по наступлению времени. Это не меняет существующий контракт сохранения будущих дат в форме рейда.
- В форме/результате сохранения явно объяснить эффект PRESENT → закрытие. Нового обязательного переключателя не добавлять.

**Приёмка / E2E.** Создать рейд с двумя PRESENT и одним ABSENT → после перезагрузки закрыты только первые двое. Проверить persisted memberId/raidId/границы периода, повтор запроса и rollback при сбое записи отметки. Продажи, доли и баланс не создаются. Чужая группа и MEMBER не могут инициировать сохранение.

## RAID-02. Пересчёт при редактировании и исправления — этап 2

**Описание.** Поддержать актуальность календаря без разрушения истории и без обхода финансовой блокировки рейда.

**Требования.**

- До финансовой блокировки изменение PRESENT → ABSENT отменяет только источник этого рейда; ABSENT → PRESENT добавляет его. Смена даты/инстанса переносит источники атомарно между соответствующими периодами.
- Несколько рейдов и ручная отметка могут подтверждать одно закрытие. Итог закрыт, если есть хотя бы один действующий источник. Отмена одного не отменяет остальные.
- После первой продажи существующие запреты на изменение посещаемости и финансовых полей сохраняются. Исправление только календаря — отдельная ADMIN-операция с причиной; она не изменяет RaidParticipant, SaleShare или LedgerEntry.
- Если разрешено исправление календаря отдельно, оно привязано к версии источника и не исчезает от повторного сохранения неизменённого рейда. Смена значимых полей требует явного разрешения конфликта.
- Деактивация персонажа и смена Main/Subclass/ника не стирают историю закрытий и исходные снимки.

**Приёмка / E2E.** Изменить дату через границу отката, инстанс и посещаемость; старый источник отменён, новый соответствует рейду. При втором источнике старый период остаётся закрытым. Финансово заблокированный рейд отклоняет запрещённый edit; отдельная календарная коррекция не меняет точные суммы долей/выплат и снимки. Два редактора получают конфликт вместо потери изменений.

## RAID-03. Старые данные и выборочный сброс — этап 2

**Описание.** Определить жизненный цикл новых сущностей в уже существующем приложении.

**Требования.**

- Старые рейды не перерабатываются молча. ADMIN видит preview: какие рейды/персонажи/периоды можно сопоставить, где нет правила, instanceId или исторической revision. Применение идемпотентно, не создаёт финансы.
- Предлагаемый reset-контракт: сброс рейдов отменяет/удаляет их источники, но сохраняет независимые ручные отметки; сброс участников очищает их привязки, отсутствия и закрытия. Сброс только продаж или выплат календарь не меняет.
- Reset preview учитывает зависимые новые записи; планировщик не отправляет сообщения из старого snapshot после сброса. Каталог предметов и правила общего каталога сохраняются. Конечный контракт требует ответа Q6.
- Данные проверяются в существующей локальной БД без её пересоздания. Добавление таблиц/ограничений — отдельная проверенная миграция, не перегенерация финансовой схемы.

**Приёмка / E2E.** Повтор применения preview не дублирует отметки; неподдержанные строки остаются видимыми. Сброс тестовой группы по выбранным категориям даёт описанный результат, чужая группа/каталог не меняются. Устаревший preview перепроверяется на сервере.
