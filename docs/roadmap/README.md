# Развитие календаря и Telegram

План по заметкам [prompts/вфі](../../prompts/вфі). Это требования к будущей разработке, а не описание уже работающих функций. Текущее поведение остаётся в [PROJECT_SPEC.md](../../PROJECT_SPEC.md).

## Согласованные границы

- Расписания и правила прокачки СА пользователь предоставит таблицей позднее. Сейчас используются только явно демонстрационные данные, связанные с существующими кодами инстансов.
- Закрытие учитывается по персонажу. При сохранении рейда инстанс автоматически закрывается для PRESENT участников.
- Порядок: календарь с ручными отметками → связь с рейдами → групповые напоминания → личный бот. Справочник СА развивается независимо после подготовки формата данных.
- Денежная информация бота доступна только в личном чате после подтверждённой привязки персонажа.
- Рейд означает уже состоявшийся поход; отдельный сценарий планирования рейдов не требуется.
- Для личного бота нужен аккаунт приложения: администратор назначает игроку одного или нескольких персонажей, игрок подтверждает Telegram-привязку.
- Групповые напоминания учитывают всех активных персонажей без исключений и без ограничения сохранённым составом.

## Минимальный первый релиз

Этапы 0–1: список ближайших откатов, статусы персонажей и ручные отметки. Не требуются Telegram, планировщик или изменения финансов. До загрузки подтверждённой таблицы это демонстрационный режим; реальные напоминания на mock-правилах запрещены.

## Общие требования к реализации

- Бизнес-правила находятся в services/repositories; формы не вычисляют источник истины. Доступ и принадлежность группе проверяются сервером на каждом чтении и изменении.
- Существующие сущности `PartyMember`, `Instance`, `Raid` переиспользуются. Ники, названия инстансов и Telegram username не служат стабильными идентификаторами.
- Деньги остаются BigInt и десятичными строками на границах. Доли, исторические снимки, ввод сумм и prefill выплат не меняются.
- Для новых экранов обязательны loading, empty, filtered empty, error/retry, pending, success, отказ доступа и конфликт устаревшей формы. Ошибка сохраняет черновик.
- Desktop — компактная матрица/список; mobile — список по инстансам или персонажам без широкой обязательной таблицы. Проверки 1440/390 px, сложных экранов также 320/768/1024 px; клавиатура, видимый фокус, текстовые статусы, touch 44 px.
- Каждая пользовательская задача включает Playwright E2E в том же изменении: основной результат, ошибки, роли, чужая группа, сохранение после перезагрузки. Chromium обязателен; полный набор запускается перед коммитом фичи. Сценарии ниже — будущие требования, сейчас они не реализованы и не запускались.
- Расчёт времени проверяется детерминированными unit-тестами; транзакции/конкуренция — подходящими интеграционными проверками. Финансовые ответы бота проверяются точными суммами по существующим проводкам.
- Тесты используют существующие локальные аккаунты и Docker PostgreSQL. Каталог предметов сохраняется. Новые БД и сбросы для подготовки не нужны. Секреты и артефакты не попадают в Git.
- До изменения Next.js читать документацию установленной версии. До изменения схемы — ARCHITECTURE.md: финансовая схема представлена в миграциях не полностью, `db push` не является безопасным способом внедрения этих фич.
- При реализации обновляются канонические документы текущего поведения: PROJECT_SPEC.md, ARCHITECTURE.md, PROJECT_CONTEXT.md и профильные спецификации. Этот план не подменяет их.

## Что исключено

Автоматическое чтение игрового клиента, гарантия фактического прохождения, учёт инвентаря/прокачки конкретного кристалла, новые расчёты выплат, переводы Adena через Telegram, создание рейдов командами бота, массовый импорт старой истории без preview. Время и бюджет отдельной интеграции с сервером сюда не входят.
