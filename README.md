# Party Bank Manager

Приложение для фарм-группы Lineage 2. Участники и игровые профили →
состав рейда → добыча → полученная оплата → равные доли → передачи Adena.
Интерфейс русский, тёмный. Локально используется PostgreSQL в Docker.
Production размещён на Vercel с общей базой Neon PostgreSQL:
https://party-bank-manager.vercel.app.
Локальный запуск production-сборки с production-БД описан в
[документации размещения](docs/DEPLOYMENT.md#локальная-production-сборка-с-production-бд).

## Запуск

Для локального запуска нужны Node.js 22.12+ или 24+, npm и Docker Desktop.
Скопируйте `.env.example` в `.env` только на новой установке; существующий `.env`
содержит локальные параметры и его следует обновить по образцу, сохраняя остальные
секреты.

```powershell
npm install
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
npm run db:up
npm run db:generate
npm run db:deploy
if (Test-Path prisma/dev.db) { npm run db:catalog:import }
npm run dev
```

Открыть [локальное приложение](http://localhost:3000). Сервер слушает `127.0.0.1`.
`DATABASE_URL` указывает на локальную PostgreSQL из `compose.yaml`.
Docker volume `party-bank-postgres-data` хранит локальные записи между перезапусками.
`npm run db:down` останавливает базу и сохраняет volume. Не использовать
`docker compose down -v`, если нужно оставить локальные данные.

При переходе с прежней локальной версии импортируйте только общий каталог предметов
из старой SQLite-базы до начала работы с новым каталогом:

```powershell
npm run db:catalog:check
npm run db:catalog:import
```

Скрипт читает SQLite только в режиме read-only и переносит записи `Item` в
PostgreSQL; тестовые рейды, участники и операции не переносятся. Исходный файл
SQLite не изменяется. `npm run db:deploy` применяет PostgreSQL-миграции и
дополнительные SQL-ограничения. Не использовать `db:push` для обновления базы.

Зарегистрируйте аккаунт на `/register`, затем создайте группу и станьте её
владельцем. `db:deploy` добавляет недостающие базовые имена High Five и metadata
инстансов административным seed; создание группы не меняет общий каталог.
Общие предметы доступны только для чтения; новые записи пользователей принадлежат
группе. Stage 1 содержит рекомендации по таблицам для Lab 78 и Fortress/Castle
Dungeon; остальные таблицы добавляются отдельно. Правила стадий и публикации:
[INSTANCE_CATALOG.md](docs/INSTANCE_CATALOG.md). Старые локальные рейды и
финансовая история не импортируются.

## Разделы приложения

| Раздел | Возможности |
| --- | --- |
| Обзор | Банк, остатки, последние рейды, раскрываемая аналитика продаж |
| Рейды | Создание, посещаемость, добыча, частичные продажи и доли |
| Финансы | Остатки участников, передачи Adena, журнал операций и CSV |
| Группа | Участники, игровые профили, сохранённые составы до 36 слотов |
| Каталог | Поиск, классификация, создание предметов и история поступлений |
| Настройки | Название группы, роли и приглашения, история действий, подключение Telegram и очистка |
| Продажи Telegram | Автоматический учёт BohPTSbot, история, уведомления, соответствия названий и повторный разбор |

Вход использует логин и пароль без email. Новый пароль — 8–128 символов,
хотя бы одна буква и одна цифра; существующие пароли продолжают работать.
Пока нет сброса или администраторской
замены забытого пароля. Храните пароль отдельно в надёжном месте. Роли участников
и правила доступа описаны в [спецификации аккаунтов](./docs/ACCOUNTS_AND_PARTIES_SPEC.md).

Продажа фиксирует уже полученную оплату. Доход делится поровну между присутствовавшими
в исходном рейде. Передача участнику может превышать начисления; отрицательный
остаток показывает переплату. Полные правила — в [описании продукта](./PROJECT_SPEC.md).

Для автоматического учёта продаж владелец подключает отдельного receiving bot
в `/settings/telegram` и выбирает групповой чат и BohPTSbot. История и исключения —
в `/telegram`; ссылка и непрочитанные уведомления доступны на страницах группы.
Английские метки пока основаны на переводе примера; настройка и поддерживаемые
форматы описаны в [Telegram-импорте](./docs/TELEGRAM_SALES_INGESTION.md).

## Резервные копии и восстановление

Резервирование и восстановление production-базы выполняются средствами Neon;
срок хранения истории и доступные способы восстановления зависят от настроек
проекта. Отдельного задания резервирования в репозитории нет.
Для локальной PostgreSQL создавайте dump через `pg_dump`; команды для PowerShell —
в [документации размещения](./docs/DEPLOYMENT.md#резервирование-и-восстановление).
SQLite-архивы прежней версии не являются способом backup/restore PostgreSQL.

Перед восстановлением сохраните текущую базу отдельно и следуйте процедуре
восстановления выбранного PostgreSQL-провайдера. Очистка данных группы не меняет
общий каталог предметов.

## Разработка и проверки

Next.js App Router, React, TypeScript strict, Tailwind CSS 4, shadcn/Base UI,
Prisma + PostgreSQL (`pg` driver adapter), Zod, React Hook Form, Vitest. Версии
закреплены в `package-lock.json`.

```powershell
npm run lint
npm run typecheck
npm test
npm run build
```

PostgreSQL integration tests выполняются только при заданном `TEST_DATABASE_URL`
для отдельной disposable базы. Legacy SQLite backup tests включаются только
через `LEGACY_SQLITE_TESTS=1` и не проверяют production-хранилище.

`npm run db:seed:demo` — отдельный инструмент записи демонстрационных данных;
не запускать его на рабочей базе для проверки интерфейса.

## Документация

Проект Vercel подключён к `OleinikovArtem/managment`; push в `master` запускает
production-деплой. Neon подключён только к Production. Серверные переменные БД,
авторизации и шифрования заданы в Vercel; секреты не хранятся в репозитории.
Production build применяет PostgreSQL migrations и SQL guards перед сборкой.
Для Preview нужна отдельная БД и отдельные секреты; текущее production-подключение
в Preview не передаётся. Процесс восстановления забытого пароля пока не реализован:
email намеренно не используется.
